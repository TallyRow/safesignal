# Contract: Bundle Invariance

**Phase**: 1 (Design & Contracts)
**Feature**: [003-rename-safesignal/spec.md](../spec.md)
**Maps to**: FR-026, SC-009, SC-010, R-013, R-015, R-016

## Purpose

The rename touches package metadata, documentation, and example
files only. It MUST NOT change runtime code, dependency pins, or
the `exports` map shape. The bundle invariance contract is the
**objective signal** that the rename did not silently leak into
build output: pre-rename and post-rename gzipped bundle sizes must
stay within ±1 KiB of each other for both the default entry and
the beacon-transport subpath entry.

A larger delta means something more than identity references
shifted, and the rename PR must be investigated before merge.

## Bundles in scope

| Bundle                          | Subpath               | Origin                                  | Tracked since |
| ------------------------------- | --------------------- | --------------------------------------- | ------------- |
| `dist/index.mjs`                | `.` (default)         | Feature 001 — core SDK + transports     | Feature 001   |
| `dist/transport-beacon.mjs`     | `./transport-beacon`  | Feature 002 — beacon transport subpath  | Feature 002   |

The `./testing` subpath (`dist/testing.mjs`) is auxiliary — used
only by consumer test suites. It is not currently locked by any
size budget but should also stay stable across the rename. Tasks
may optionally include it in the invariance check.

The baseline is captured by running `npm run build` against the

two bundles in scope.

The baseline values from the project status snapshot at the start

These baselines are **frozen at the time of feature 003's branch

## Invariance assertion

For each bundle in scope, after all rename edits are applied and
`npm run build` re-runs:

```text
abs(post_rename_gzipped - pre_rename_gzipped) <= 1024 bytes
```

`1024 bytes` (1 KiB) is the ±tolerance from SC-009. Any larger
delta fails the invariant.

### Rationale for the ±1 KiB tolerance

Even though the rename does not change runtime code, the
`package.json` `name` field is embedded in the published `dist/`
artifacts in trivial ways (e.g., in `dist/index.d.ts`'s comment
header generated by tsup, or in the `// @ts-self-types` pragma).
The string `@tallyrow/safesignal` is shorter than
`@your-org/frontend-logging-sdk` by 6 chars (uncompressed), so the
expected delta is in fact **slightly negative** post-rename
(smaller). The ±1 KiB tolerance comfortably covers this trivial
delta plus any minor toolchain noise (compression level variance,
timestamp embedding, etc.). A delta outside ±1 KiB is highly
unlikely to be benign and warrants investigation.

The rename also requires that the following pre-existing checks
pass unchanged. These are not part of "bundle invariance" per se

gate:

**Verification**: `npm test -- tests/contract/dependency-pins.test.ts`
exits 0 with the same assertion count.

### `tests/security/bundle-shape.security.test.ts`

Locks the source-import boundary scan + the gzip budget for the

unchanged.

## Verification workflow

1. From the rename branch, BEFORE any edits, run:
   ```bash
   npm run build
   gzip -c dist/index.mjs | wc -c
   gzip -c dist/transport-beacon.mjs | wc -c
   ```
   Record the values as `baseline_index_gz` and `baseline_tb_gz`.

2. Apply all rename edits (per the tasks.md sequence).

3. Run:
   ```bash
   npm run build
   gzip -c dist/index.mjs | wc -c
   gzip -c dist/transport-beacon.mjs | wc -c
   ```
   Record the values as `post_index_gz` and `post_tb_gz`.

4. Assert:
   ```text
   abs(post_index_gz - baseline_index_gz) <= 1024
   abs(post_tb_gz    - baseline_tb_gz)    <= 1024
   ```

5. Run `npm test` and confirm all three preserved tests
   (`dependency-pins`, `bundle-shape`, `transport-beacon-bundle-shape`)
   pass unchanged.

## Pass / Fail criteria

- **PASS**: Both bundles within ±1 KiB gzipped, AND all three
  preserved tests pass with the same assertion counts as pre-rename.
- **FAIL**: Either bundle exceeds ±1 KiB gzipped, OR any preserved
  test fails or changes assertion count.

A FAIL means runtime/exports/dependency state shifted unexpectedly;
the rename PR must be investigated before merge.
